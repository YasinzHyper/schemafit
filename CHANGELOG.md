# Changelog

All notable changes to this project are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project adheres to [Semantic Versioning](https://semver.org/).

## Unreleased

### Added

- Fix infrastructure: a rule may attach a `fix` to a finding, a pure rewrite of the subschema the finding points at. `Finding.fix` carries its `title` and `rewrite`, and `RuleMeta.fixable` marks the rules that always attach one.
- `fix(schema, { providers })`: applies every available fix, re-linting until the schema settles, and returns the rewritten schema, the fixes applied, and the findings that remain. The input schema is never mutated.
- `schemafit --fix --provider <id> <file>`: writes the rewritten schema to stdout or `--out <file>`, and reports what changed on stderr. The schema is put back into the tool or `response_format` wrapper it came from, so a fixed tool definition keeps its other fields.
- `unwrap` now also returns `keys`, the path from the document to the schema, and `rewrap` puts a rewritten schema back there.
- A fix for `openai/additional-properties-false` and `anthropic/additional-properties-false`: set `additionalProperties: false` on every object that does not.
- A fix for `openai/all-required`: adds every property missing from `required` and makes it accept `null`, which is how the OpenAI docs keep a field optional under strict mode. A `type` gains `"null"`, an `anyOf` gains a `{ "type": "null" }` branch, and a `$ref` is wrapped in one. A property with no `type` to extend (a bare `enum` or `const`) is required as it is, and the reported fix title says which properties were made nullable.
- A fix for `openai/no-one-of`: renames `oneOf` to `anyOf`, keeping the branches and the position of the keyword. The rename widens the union from exactly one matching branch to at least one, which the rule's notes spell out. A schema that already has an `anyOf` of its own is reported without a fix, because the two cannot be merged without changing what the schema accepts.
- A fix for `anthropic/no-numeric-constraints`, `anthropic/no-string-length`, and `anthropic/array-constraints`: the unsupported keyword is removed and what it required is stated in `description` ("Must be at least 100."), which is the transformation the Anthropic SDKs apply. `minItems` is lowered to 1 rather than removed, because 0 and 1 are supported. A keyword whose value cannot be put into words, such as a draft-04 boolean `exclusiveMinimum`, is still reported but carries no fix, and a `uniqueItems: false` is dropped without a note.
- A fix for `openai/unsupported-format` and `anthropic/unsupported-format`: the unsupported `format` is removed and what it required is stated in `description`, so `"format": "uri"` becomes "Must be an absolute URI, such as https://example.com/a." Every format the JSON Schema format vocabulary defines has its own wording; anything else, such as a generator's `int64`, is named as it stands ("Must be a string in the \"int64\" format."). `gemini/undocumented-format` deliberately carries no fix, because the Gemini docs list their formats with "such as" and a format that is only undocumented may well work. With this, `examples/ticket.json` comes out of `--fix --provider openai` compatible rather than with one error left.
- A fix for `openai/unsupported-composition`: an `allOf` whose branches are plain objects is merged into the object that holds it, with the properties of every branch on one object, the union of their `required` keys, and their descriptions joined. Merging widens an `additionalProperties: false` declared in a branch, which then no longer rejects the properties of its siblings, and a single strict object has to accept those anyway. Branches that constrain the same key differently carry no fix, and neither do `not`, `if`/`then`/`else`, `dependentRequired`, and `dependentSchemas`, because dropping them would change what the schema accepts.
- A fix for `openai/root-object`: a root OpenAI will not take — a union, an array, a primitive — is wrapped in an object with one required property, `result`, and the fix title names that key, because the model then answers `{ "result": ... }` instead of the bare value. `$defs` and `definitions` stay at the root, so `#/$defs/...` references keep resolving, and everything the root said about the value it accepts moves inside the wrapper. A root that carries nothing but definitions has nothing to wrap and is reported without a fix.
- The fix for `openai/unsupported-composition` now inlines an `allOf` branch that is nothing but a local `$ref`, so the `{ "allOf": [{ "$ref": "#/$defs/User" }], "description": "..." }` that Pydantic emits for an annotated model field merges like any other branch. A `$ref` is not inlined when the definition it names refers back to itself, which cannot be inlined at all.
- A definition that more than one subschema references is now inlined too, as a copy: the original stays where it is, for the references the fix does not touch, and the fix title says which definition was copied ("Merge the \"allOf\" branch into the object, copying #/$defs/user, because the schema references it elsewhere too."). Two fields annotated with the same Pydantic model produce exactly this shape, and leaving it alone left an `allOf` that no fix could resolve and the API rejects. What the copy costs is size, and the property, nesting, and string-size rules measure it again over the fixed schema.
- `schemafit rules` marks fixable rules with `[--fix]`, and `docs/rules.md` records them as fixable.
- `schemafit --fix --prune-unused-defs`, and `fix(schema, { pruneUnusedDefs: true })`: remove every `$defs` / `definitions` entry that no `$ref` reaches, not only the ones a rewrite orphaned, together with anything only those entries referenced and the definition maps they empty. It stays behind a flag because it is a different decision from the prune a fix does itself: a definition the author wrote and never referenced changes nothing about what the schema accepts, and another document may `$ref` into it. What it buys is the property and string-size budget an unused definition spends for nothing, which a generator that emits one `$defs` map per module hands out freely. Pruning runs before the first lint, so no fix is spent rewriting a definition that is about to go, and again after each pass. Nothing at all is pruned from a schema whose references cannot all be followed — an anchor (`"$ref": "#user"`), a `$dynamicRef`, a `$recursiveRef`, a URL, or a subschema with its own `$id` — because a definition that *is* referenced would look unused and go. Whether they can be followed is decided by reading the whole document as plain JSON rather than the subschemas the walker visits, so a reference under a keyword it does not know — draft-07 `dependencies`, a `contentSchema` — stops pruning as well: a reference nothing can see would neither stop pruning nor hold its definition in place, and the schema would come back with a `$ref` pointing at nothing.
- A fix may now name the definitions its rewrite could orphan, in `SchemaFix.prunes`, and `fix()` removes each one once nothing outside it holds a local `$ref` to it any more, together with the `$defs` or `definitions` map it empties. The removal is reported like any other fix, pointing at the definition that went. The fix for `openai/unsupported-composition` uses it, so inlining the `{ "allOf": [{ "$ref": "#/$defs/User" }] }` that Pydantic emits no longer leaves `#/$defs/User` behind, and a definition that was copied because several subschemas referenced it goes once the last of them is inlined. An orphan is not free: OpenAI counts definition names toward the 120,000-character string budget and every property below them toward the 5000-property limit. A definition that was already unreferenced before the fix ran is left alone. Only an entry of a definition map that belongs to a subschema is removed, so a property *named* `$defs` or `definitions` keeps everything it describes: a local `$ref` may point at any subschema, and the `items` of a `#/properties/$defs` array is a constraint the schema declares rather than a definition to prune. A definition is held in place by every reference in the document, wherever it sits, not only by the ones under a keyword the walker visits, so a `$ref` in a draft-07 `dependencies` keeps its definition and the `allOf` fix copies it instead of moving it out from under it.

- A file may now hold more than one schema, and each one is linted, fixed, and reported on its own. A whole request body declares several: `tools: [...]` for OpenAI, Anthropic, and Gemini alike, the nested `tools` of an OpenAI namespace, `response_format` for Chat Completions and for Gemini, and `text.format` for the Responses API. An MCP `tools/list` response is that same `tools` array with MCP's spelling of the schema key, and a bare JSON array of tool definitions works too, whose entries may also be bare schemas. The report names each schema by where it sits and what the definition is called (`request.json#/tools/1/input_schema  create_ticket`), and the JSON output carries that as `pointer` and `name`. The pointer is what tells several reports on one file apart, so a document that holds a single schema is still reported by its file name alone; what is new there is the tool's name beside it. A tool that declares no schema is skipped rather than linted as if the definition were one, which is what a server tool such as Anthropic's `web_search` or an OpenAI built-in looks like, and a document in which nothing declares a schema is a usage error instead of a silent pass. `--fix` rewrites every schema the document holds and puts each back where it came from, so a fixed request body keeps its model, its messages, and the tools it had nothing to change in.

- `unwrapAll(document)`: every schema a document holds, each with the `wrapper` it was found in, the `keys` and `pointer` that lead to it, and the `name` its definition carries. `unwrap` is unchanged, for a document that holds exactly one.

- `examples/messages-request.json`: an Anthropic Messages request body with two client tools and a server tool, which is what `schemafit` is pointed at when the schemas never existed as files of their own.

- The fix for `openai/unsupported-composition` now merges an `allOf` branch that describes something other than an object. Object branches still contribute their properties, required keys, and descriptions; any other branch contributes the constraint it declares, narrowed to what every branch agrees on — the types and enum values they have in common, the larger of two lower bounds, the smaller of two upper bounds. So `{ "allOf": [{ "$ref": "#/$defs/Priority" }], "description": "How urgent it is." }` over a `{ "type": "string", "enum": [...] }` definition — the shape a generator emits for an annotated enum field, where the description could not sit beside the reference — merges like any object branch does, and the definition is pruned once nothing references it. The fix title says "into the schema" rather than "into the object" when the result is not an object. Branches with no type or enum value in common are left alone, because an `allOf` nothing can match is not something a rewrite should paper over, and so is a branch that carries a `$ref` beside other keywords: there is nothing to inline, and merging would put the reference next to those keywords, which the documented subset does not describe.

- `schemafit --fix` now rewrites for every provider it was given, not just one, and with no `--provider` for all of them: the output is the most portable schema the rules can reach, the one OpenAI, Anthropic, and Gemini all accept. Each provider's fixes land on the same schema and the schema is re-linted after every pass, so a rewrite that exposes another provider's finding is fixed in the next one. Portability is not free — the rewrite gives up the constraints only some providers support, such as the `minimum` OpenAI keeps and Anthropic does not — so naming the providers you ship to still keeps everything the others would have rejected. The `--fix` report ends with one line per selected provider, aligned the way the lint report aligns them.

- `examples/invoice-tool.json`: an OpenAI tool whose schema reuses its definitions — one referenced twice, once through an `allOf` and once directly, and one annotated with a description that could not sit beside the reference. It is the shape a generator emits for a field typed as another model, and the one the `allOf` rewrites were built for: `--fix` with no `--provider` turns it into a tool OpenAI, Anthropic, and Gemini all accept.

- A round-trip test over `examples/`: every example is rewritten for each provider on its own and for all of them at once, and what `--fix` leaves behind is recorded per example and per provider. Each run asserts that no finding carrying a fix survived, that fixing the output again changes nothing, that every local `$ref` still resolves after the inlining and pruning, that the compatibility verdict matches the errors left, and that the rewritten schema goes back into the wrapper it came from. An example added without its outcome recorded fails the test, and so does a provider added without being checked.

- A fix for `anthropic/allof-ref`: the definition a bare `$ref` branch names is put in the branch's place, and the `allOf` stays where it is. That is the whole fix here, because the Anthropic docs list `allOf` among the supported keywords and single out only an `allOf` that contains a `$ref` — unlike the `openai/unsupported-composition` merge, which has to dissolve the `allOf` as well. A definition other subschemas reference too is copied rather than moved, and the fix title says so; one the inlining leaves with no references at all is removed, together with the `$defs` map it empties. A branch carrying a `$ref` beside other keywords is still reported without a fix, because inlining would have to intersect the definition with those keywords, and so is a `$ref` that cannot be resolved or that names a definition referring back to itself, which `anthropic/no-external-ref` and `anthropic/no-recursive-schemas` report in their own right. With this, `--fix --provider anthropic` turns `examples/invoice-tool.json` into a tool Anthropic accepts, where it used to leave two errors the tool could in fact rewrite.

- `schemafit --fix --write <file...>`: rewrite every file given in place, so `--fix` can run over a directory of schemas or from a pre-commit hook rather than one file at a time into stdout or `--out`. Every file is read and rewritten before any of them is written out, so a file that cannot be read or is not JSON fails the run instead of leaving the files ahead of it rewritten and the rest untouched. A file no fix changed is not written at all, which keeps its formatting and its mtime as they were; the files that were rewritten come back with two-space indentation. The report of each file still goes to stderr, followed by a line counting how many of them changed. `--write` cannot be combined with `--out`, and it cannot rewrite stdin.

- Anthropic's request-wide complexity limits are now measured across every schema of a request, not one schema at a time: `anthropic/strict-tools-limit` (new) reports more than 20 tools carrying `"strict": true`, and `anthropic/optional-parameters-limit` and `anthropic/union-parameters-limit` add up the optional and union parameters of every schema the request sends strictly. That is how the docs state them — "these limits apply to the combined total across all strict schemas in a single request" — and it is the case they warn about: four strict tools with six optional parameters each reach the limit of 24 though no single tool looks complex. The findings are reported for the request as a whole, after the reports on its schemas, and the message names what each schema contributed (`The request's 4 strict schemas have 28 optional parameters; the request-wide limit is 24 (tool_0 7, ...)`). A tool that sets `"strict": false` is left out of every total; one that says nothing about `strict` is counted, as is a file that holds nothing but a schema. Only tools carrying `"strict": true` count toward the limit of 20, because the docs say non-strict tools do not.

- `lintRequest(document, { providers })`: the request-wide rules over every schema a document holds, with each finding's `path` a JSON Pointer from the document and `""` the request as a whole. `lintSchema(schema)` is the rules that check one schema, without them. `lint(schema)` is unchanged: it is the two together, measuring a request that holds one schema.

- `requestSchemas(document)`, `requestRules`, and the `RequestRule` / `RequestContext` / `RequestSchema` types, so a rule can measure a request the way a `Rule` measures a schema. `schemafit rules` marks such a rule `[request]`, and `docs/rules.md` records its scope.

- `unwrapAll` now finds the schema of an Anthropic JSON output (`output_config.format`, and the `output_format` it is deprecating) as well as the OpenAI and Gemini spellings, so a Messages request body that asks for structured output is linted whole. Every entry also carries `kind` — whether a tool or an output format declared the schema — and `strict`, what the declaration says about strict decoding, which is what the request-wide limits count.

- Only the schemas a document sends strictly are checked: a tool or output format that sets `"strict": false` is left out of the report, and `--all-tools` checks it anyway. These rules describe the subset a provider accepts under strict decoding, and a declaration that opts out of strict decoding opts out of the subset with it — OpenAI calls such a tool "non-strict, best-effort function calling" and rejects a schema only "if you send `strict: true` and your schema does not meet the requirements", and a non-strict Anthropic tool's `input_schema` is never compiled into a grammar — so reporting the subset against one was a false positive. A declaration that says nothing about `strict` is still checked, because a Responses request "will attempt to normalize your schema into strict mode when possible" and whether the subset is met is what decides whether it can. `--fix` honours the same split: a non-strict tool is left exactly as it was, keeping the `minLength` or `format` a rewrite would have moved into its `description` for nothing. A note on stderr names what was left out, and a document whose every schema opts out says so and exits 0 rather than passing silently. The request-wide limits are unaffected: they already counted the strict schemas only, and they still measure the request whether or not its schemas were reported on.

- `examples/chat-request.json`: an OpenAI Chat Completions request body with one tool sent strictly and one deliberately left non-strict, which is the split `--all-tools` turns off. The non-strict tool carries the `minLength`, `maxLength`, and `uniqueItems` that strict mode would have cost it.

- An MCP `tools/list` response is now accepted in the JSON-RPC envelope it arrives in (`{ "jsonrpc": "2.0", "id": 1, "result": { "tools": [...] } }`), so a response captured off the wire or saved from a client log can be linted and fixed as it is, without lifting `result.tools` out of it by hand first. Every MCP message follows JSON-RPC 2.0, and a result response carries its payload under `result`, so that is the only place in an envelope a schema is looked for: the tools are reported at `#/result/tools/0/inputSchema`, and `--fix` puts each rewritten schema back inside the envelope, which comes out whole down to its `id` and `nextCursor`. A JSON-RPC message that declares no schema — a request, a notification, an error response, or the result of a method that returns no tools — is reported as holding none instead of being linted as if the envelope itself were a schema.

- `examples/mcp-tools-list.json`: a captured `tools/list` response from a notes server, inside its JSON-RPC envelope, with the pagination cursor a first page carries.
- A JSON-RPC message that declares no schema is now named for what it is instead of reported as a document that holds none: an error response names the `code` and `message` of the call that failed, a request and a notification name their `method`, and a result that is some other method's payload says so. `jsonRpcMessage(document)` returns the same reading for library callers.
- A JSON-RPC batch is now read as the array of envelopes it is, so every tool of every response in a captured batch is reported under the index of its own message (`#/1/result/tools/0/inputSchema`), and `--fix` rewrites each of them and puts the batch back together, down to the messages that declare no schema. The specification defines a batch as "an Array filled with Request objects", answered with "an Array containing the corresponding Response objects"; MCP required batching through revision 2025-03-26 and dropped it in 2025-06-18, so a captured batch comes from a server of that vintage or from another JSON-RPC service. Until now such a file was read as a bare array of schemas and each envelope was linted as if it were one, which reported findings against the protocol rather than against the tools. An array is a batch when any entry in it is a JSON-RPC message — no schema or tool definition declares a `jsonrpc` of `"2.0"` at its root, and the specification's own batch example mixes messages with an entry that is none — so an array of tool definitions is read exactly as before. A batch that declares no schema names each of its messages, up to three of them and a count of the rest, and `jsonRpcBatch(document)` returns the same reading for library callers.

### Changed

- `anthropic/optional-parameters-limit` and `anthropic/union-parameters-limit` moved from the rules that check one schema to the rules that measure a request, so a request body over the limit is now reported even when every tool in it fits. A file that holds one schema is measured as a request that holds one, which is what it was before.
- `AppliedFix.ruleId` and `AppliedFix.provider` are now optional: a rewrite that no finding asked for, which today means a definition `--prune-unused-defs` removed, has no rule behind it. The `--fix` report names the flag where it would name the rule.
- Every Anthropic rule was re-checked against the structured outputs documentation and now records `2026-10-03` as its verification date. The supported and unsupported keyword lists, the string formats, the regex features, the enum-casing caveat, and the 24 optional and 16 union parameter limits are unchanged.
- Every OpenAI rule was re-checked against the Structured Outputs documentation and now records `2026-09-22` as its verification date. The supported types, string formats, per-type keywords, unsupported composition keywords, and the nesting, property, enum, and string-size limits are unchanged.

## 0.1.0 - 2026-09-17

### Added

- `lint(schema, { providers })` library API and the `schemafit` CLI (`pretty` and `json` output, stdin, `--quiet`, `--max-warnings`, `rules` subcommand).
- OpenAI Structured Outputs rules: root object, all fields required, `additionalProperties: false`, unsupported composition keywords, `oneOf`, string formats, undocumented keywords, nesting depth, and the property, enum, and string-size limits.
- Anthropic structured outputs rules: `additionalProperties: false`, recursion, external `$ref`, enum value types, numeric, string, and array constraints, string formats, `allOf` with `$ref`, regex features, optional- and union-parameter limits, and enum casing.
- Gemini structured output rules: keywords and string formats outside the documented subset.
- Automatic unwrapping of OpenAI tool and `response_format` definitions, Anthropic tools, and MCP tools.
- `docs/rules.md`, generated from rule metadata, with the documentation source and verification date of every rule.
